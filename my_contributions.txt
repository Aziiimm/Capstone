================================================================================
MY CONTRIBUTIONS TO THE CAPSTONE PROJECT
GPU-Accelerated Hybrid Amazon Recommender
================================================================================

Project Summary:
The project builds a recommendation system on the Amazon Reviews 2023 dataset,
comparing a CPU baseline pipeline against a GPU-accelerated pipeline using
NVIDIA RAPIDS (cuDF/cuML). The system incorporates sentiment analysis from
review text and targets a 10x-50x speedup on an RTX 2080 Ti (11GB VRAM).

--------------------------------------------------------------------------------
1. GPU FOLDER — gpu/recommender.py
--------------------------------------------------------------------------------

I completed the entire GPU folder, which contains the core GPU-accelerated
recommender logic in recommender.py.

What recommender.py does:
- Implements a GPU-based collaborative filtering recommender using RAPIDS
  (cuDF + cuML) and CuPy.
- Reads cleaned Parquet files produced by the CPU data pipeline and loads
  them directly into GPU memory using cuDF, keeping data on the device.
- Builds a dense user-item rating matrix on the GPU using CuPy arrays,
  mapping arbitrary reviewerID and ASIN strings to contiguous integer indices
  via cuDF categorical encoding.
- Fits a cuML NearestNeighbors (KNN) model on the user vectors stored entirely
  in GPU memory using cosine similarity by default.
- Implements recommend_for_user(), which takes a user ID, finds that user's
  K nearest neighbor users via KNN, aggregates their ratings through mean
  scoring, excludes already-seen items, and returns the top-K recommended
  ASINs.
- Includes a batch_recommend() convenience helper for recommending across
  many users at once.
- Handles the case where RAPIDS is not installed gracefully — the import fails
  cleanly with a helpful RapidsNotAvailableError rather than crashing silently.

Why I built it this way:
The whole point of this project is to compare CPU vs GPU performance on the
same recommendation task. I wanted a GPU recommender that mirrors the same
KNN collaborative filtering logic that the CPU side would use, so the two can
be benchmarked head-to-head. The GPU version keeps all matrix operations
(neighbor search, score aggregation, top-K extraction) on the GPU and only
transfers final item ID results back to the CPU, minimizing host-to-device
transfer overhead — which is one of the key benchmarking metrics defined in
the project plan.

2. NOTEBOOKS — notebooks/nlp_clean.ipynb
--------------------------------------------------------------------------------

I completed the NLP cleaning notebook, which serves as Week 3's deliverable
per the project timeline (nlp_clean.ipynb).

What the notebook does:
- Loads the cleaned Parquet sample produced by the CPU data pipeline.
- Implements a clean_review_text_pandas() function that lowercases text,
  strips all non-alphanumeric characters, collapses whitespace, and strips
  leading/trailing spaces — all in Pandas on CPU.
- Times the CPU cleaning pass and prints wall-clock performance.
- Implements the equivalent clean_review_text_cudf() GPU version using cuDF
  string operations that mirrors the same regex and cleanup steps.
- Times the GPU cleaning pass and prints the speedup factor vs Pandas.
- Falls back gracefully if cuDF is unavailable, printing a message that the
  CPU-cleaned column is the deliverable for the week.
- Saves the cleaned DataFrame (with reviewText_clean column added) back out
  to a sample_clean.parquet file.

This notebook directly enables the hybrid sentiment scoring step (Phase 2 of
the project plan), which produces the sentiment-adjusted rating:
  hybrid_score = (0.7 * rating) + (0.3 * normalized_sentiment)

3. KERNELS FOLDER — kernels/ (Scrapped)
--------------------------------------------------------------------------------

I wrote five custom CUDA C++ kernel stubs in the kernels/ folder. These were
intended to be hand-written low-level CUDA kernels to replace or supplement
the RAPIDS cuML layer. After working through them, I made the decision to
scrap this approach and rely on RAPIDS instead.

The five kernels I designed and stubbed out:

  01_sentiment_tokenizer.cu (Difficulty: 65/100)
    - GPU kernel to tokenize raw review text stored as a flattened character
      array with offset indices.
    - Each thread processes one review, iterates over characters, identifies
      words, and performs a device-side sentiment dictionary lookup.
    - Challenge: variable-length strings cause thread divergence and unbalanced
      workloads across thread blocks.

  02_matrix_factorization_sgd.cu (Difficulty: 85/100)
    - SGD-based matrix factorization kernel updating user and item latent
      factor embeddings in parallel.
    - Each thread handles one user-item interaction from a batch, computes
      the predicted rating as a dot product, calculates the error, and
      applies gradient updates using atomicAdd to avoid race conditions.
    - Challenge: multiple threads updating the same item embedding
      simultaneously requires atomic operations or graph coloring strategies.

  03_sparse_similarity.cu (Difficulty: 70/100)
    - Sparse cosine similarity kernel operating on CSR (Compressed Sparse Row)
      format user-item matrices to avoid O(N^2) dense similarity matrices.
    - Each thread computes the cosine similarity between one user and a target
      user using two-pointer intersection over sparse columns.
    - Challenge: indirect memory accesses in CSR format can defeat coalesced
      reads if thread blocks are not carefully organized.

  04_top_k_retrieval.cu (Difficulty: 80/100)
    - Block-wide Top-K retrieval kernel using one thread block per user.
    - Threads cooperate via shared memory to maintain a parallel min-heap,
      extracting only the top-K items without sorting the full predictions.
    - Also evaluates Hit Ratio (HR@K) inline on the GPU.
    - Challenge: implementing an efficient parallel min-heap or bitonic sort
      with __syncthreads() synchronization is notoriously difficult to
      get right for performance.

  05_graph_aggregation.cu (Difficulty: 90/100)
    - Graph Neural Network message-passing kernel for LightGCN/GraphSAGE-style
      aggregation on a user-item bipartite graph.
    - Each thread handles one edge, loading the source node embedding,
      multiplying by the edge weight (sentiment score), and atomically
      scattering it into the destination node's output embedding.
    - Challenge: power-law degree distributions in real recommendation graphs
      mean some nodes have millions of edges while others have one, causing
      severe load imbalance across warps and thread blocks.

Why scrapped:
Implementing production-quality CUDA kernels for all five of these operations
would have been extremely time-consuming and error-prone, especially given
the race condition and memory coalescing challenges documented above. RAPIDS
cuML already provides optimized, production-tested implementations of KNN and
related algorithms. Switching to RAPIDS keeps the project on schedule and lets
us focus on the actual benchmarking and hybrid recommendation logic rather
than low-level CUDA debugging. The kernel stubs are preserved in the repo as
documentation of the original low-level approach.

4. WHAT STILL NEEDS TO BE DONE (per the project plan)
--------------------------------------------------------------------------------

Based on the PLAN.md and README.md, the following are not yet implemented:

Phase 2 — Hybrid Feature Engineering:
  - Sentiment scoring is not yet integrated into the data pipeline. The
    nlp_clean notebook cleans text but does not produce sentiment scores yet.
  - The hybrid_score = (0.7 * rating) + (0.3 * normalized_sentiment) fusion
    has not been implemented.
  - Cold-start logic for new users (recommend from sentiment of initial text
    input only) is not yet built.

Phase 3 — CPU Baseline Recommender:
  - There is a GPU recommender (gpu/recommender.py) but there is NO matching
    CPU recommender yet. The plan explicitly calls for a dual-pipeline
    implementation using Scikit-learn or Surprise for the CPU side.
  - Without a CPU recommender, the head-to-head benchmarking (the core thesis
    of the project) cannot be completed. This is a critical gap.

Phase 3 — Benchmarking Infrastructure:
  - Host-to-Device data transfer timing is not yet measured or reported.
  - A unified benchmarking script that runs both CPU and GPU pipelines and
    outputs the Speedup Factor is not yet built.

Phase 4 — Serving & Frontend:
  - No inference server (Flask or NVIDIA Triton) has been built yet.
  - No React dashboard has been built yet.

Evaluation Metrics:
  - NDCG@K and Precision@K evaluation code has not been written yet.
  - The latency measurement (ms per single user recommendation) has not been
    implemented.
